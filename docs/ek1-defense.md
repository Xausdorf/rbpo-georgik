## M1: продукт и запуск, слайды 1–2, 90 секунд

> Наш продукт GetFast — серверное API городской доставки посылок. Отправитель оформляет посылку, диспетчер назначает курьера, курьер забирает и вручает её по коду. Получатель может узнать статус по трек-номеру без регистрации. Оплата, карты и мобильное приложение находятся за границей проекта. Работаем с учебными данными.
>
> В текущей основной ветке есть минимальная запускаемая основа: ASP.NET Core на .NET 10, подключение к PostgreSQL, контейнерный запуск и Swagger. Это позволяет уже сейчас подтвердить существование технического объекта, к которому относится концепция безопасности.
>
> Показываю GET /health. Если база доступна, сервер возвращает HTTP 200 и status healthy. Отрицательные проверки также предусмотрены: при недоступной базе ответ 503, без пароля или строки подключения в ответе. Документы пока описывают будущие защитные механизмы. Успешный health не доказывает защиту отправлений или кода получения.
>
> Основные риски связаны с адресами и телефонами, полномочиями сотрудников и ложным вручением посылки. Дальше покажем, как связываем эти риски с требованиями и решениями.

Демо включено в эти 90 секунд: заранее открыть Swagger, нажать GET /health, Try it out, Execute. Команда запуска и результат — в README. Если слот короче, показать прямой ответ /health.

## M2: доверие и доступ, слайды 3–4, 90 секунд

> Пользователь может вызвать API напрямую и изменить запрос, поэтому интерфейс не является защитой. В нашей модели одна граница проходит между клиентом и сервером. Другая проходит между полномочиями ролей: курьер входит в систему, но не получает право на чужие задания. Публичное отслеживание имеет отдельную анонимную границу и должно раскрывать минимум сведений.
>
> В приоритетный набор входят подстановка чужого ID, выход курьера за свои задания, повышение роли, перебор и утечка кода. У них серьёзные последствия, а способ атаки доступен в основных сценариях.
>
> Для доступа к объектам цепочка такая: T-01 и T-02, затем SR-01 и SR-02, затем D-01. Сервер выбирает отправление сразу с условием владельца, а задание — с условием назначенного курьера и активного статуса. Чужой объект и отсутствующий объект дают одинаковый 404. GUID затрудняет угадывание, но не заменяет эту проверку.
>
> D-02 закрывает повышение роли: сервер сам назначает роль при регистрации, а группы методов требуют соответствующие полномочия. Проверка роли и проверка владельца нужны вместе. Будущая проверка D-01 сравнит доступ двух отправителей и двух курьеров, включая доступ после завершения задания. Эти проверки ещё не выполнены в текущем каркасе.

## M3: код получения, слайды 5–6, 90 секунд

> Моя цепочка относится к коду получения. T-03 — курьер перебирает код и отмечает вручение без получателя. T-10 — код утекает из карточки, базы или журнала. SR-06 требует верный одноразовый код и блокировку после пяти ошибок. SR-07 ограничивает выдачу кода владельцем и запрещает его хранение в восстановимом виде.
>
> В D-03 мы выбрали шесть случайных цифр и хранение HMAC-SHA256 от идентификатора отправления и кода. HMAC использует секретный ключ вне базы. Обычный хеш короткого кода позволяет проверить все миллион вариантов по украденной базе. HMAC без ключа такой проверки не даёт. Код показываем владельцу один раз. Если он потерян, владелец получает новый, а старый перестаёт действовать.
>
> Контрпример: если разрешить показывать код в карточке постоянно, сервер должен хранить его в восстановимом виде. Ошибка ответа диспетчеру раскрыла бы действующие коды. Поэтому мы сравнили шифрование с одноразовым показом и выбрали второй вариант, приняв неудобство перевыпуска.
>
> Счётчик ошибок, статус и событие журнала планируем сохранять одной транзакцией с проверкой версии строки. Десять параллельных неверных запросов не должны обходить лимит пяти. Перевыпуск не обнуляет счётчик. Проверим также старый и новый код, отсутствие кода в ответах и журналах, забор против отмены. Это план механизма, реализация D-03 ещё впереди.

## Вопросы каждому

### M1

- **Что доказывает /health?** API запускается и может связаться с базой. Правильность бизнес-сценариев и защиты оно не доказывает.
- **Почему роль из тела регистрации опасна?** Клиент может подставить Dispatcher. Роль назначает сервер, неизвестные поля регистрации отклоняются по D-02.
- **Нужен ли весь продукт к EK1?** Нет. Нужны связная концепция, минимальная запускаемая основа и личное понимание. Источник — регламент EK1.

### M2

- **Чем роль отличается от доступа к объекту?** Sender разрешает группу методов, а владелец определяет конкретные отправления. Courier не разрешает чужие задания.
- **Почему не достаточно GUID?** Чужой ID можно узнать. Право проверяется независимо от сложности угадывания ID.
- **Почему 404 вместо 403?** Ответ не подтверждает наличие чужого объекта.
- **Почему проверка в запросе?** Без условия доступа объект вообще не выбирается. Это уменьшает риск забыть отдельную проверку после загрузки.

### M3

- **Что такое HMAC простыми словами?** Проверочное значение, рассчитанное из кода и секретного ключа. Сервер сравнивает значения и не хранит сам код.
- **Чем HMAC отличается от шифрования?** Шифрование позволяет восстановить код ключом. HMAC предназначен для проверки, восстановление не предусмотрено. С ключом и базой короткие коды всё равно можно перебрать.
- **Почему обычный хеш не подходит?** Код состоит из шести цифр, всего миллион вариантов. Обладатель базы может посчитать хеш каждого. Публичная соль не делает короткий код неперебираемым.
- **Почему пять попыток?** Для равномерного случайного кода вероятность угадать за пять разных попыток не выше 5 / 1 000 000, то есть 0,0005%. Лимит должен сохраняться на сервере и выдерживать параллельные запросы. Это оценка при сохранении секретности кода и ключа.
- **Зачем идентификатор отправления в HMAC?** Одинаковый код у двух посылок даёт разные проверочные значения, их нельзя переносить между отправлениями.
- **Что такое xmin?** PostgreSQL меняет системную версию строки при обновлении. Сервер сохраняет изменение только для прочитанной версии и обнаруживает, если другой запрос уже изменил строку.
- **Зачем транзакция?** Статус, число ошибок и запись события должны сохраниться вместе. Нельзя получить «доставлено» без события или событие вручения без изменения статуса.
- **Что если запросы приходят одновременно?** Проверка версии не даёт двум переходам успешно изменить одну исходную версию. Для ошибок кода возможен повтор с новым чтением и повторной проверкой лимита.
- **Почему изменили гонку «вручение / возврат»?** Они разрешены из разных статусов. Для проверки двух допустимых конфликтующих действий используем забор и отмену из «ожидает забора» или вручение и неудачную попытку из «в доставке».
- **Что при утрате кода?** Владелец перевыпускает его. Новый отличается от старого. Число ошибок не сбрасывается, после блокировки перевыпуск отклоняется.
- **Что механизм не защищает?** Сговор, добровольная передача кода постороннему, компрометация ключа вместе с базой. Курьер также может намеренно вызвать блокировку, это фиксируем в журнале.
- **Где реализация D-03?** В оцениваемом каркасе её пока нет. Есть решение и конкретные будущие проверки. Нельзя утверждать, что лимит или HMAC уже работают.

## Перед фиксацией версии

1. Каждый участник читает и проверяет свою часть. В AI_USAGE указываются только фактические человеческие проверки. Историю раннего использования ИИ дополняют авторы материалов.
2. Команда подтверждает коды M1–M3, согласование темы и закрытую регистрацию. Поле «черновик» меняется только при наличии подтверждения преподавателя.
3. Команда выбирает, какие проверенные изменения включить в оцениваемую версию. Открытый PR сам по себе не входит в main. При включении M1/auth-roles актуализируются заявления о текущем состоянии и повторяется демо.
4. Один участник передаёт URL и существующий commit hash либо tag ek1 через объявленный канал до объявленного срока. Не перемещать уже сданный tag самостоятельно.
5. По переписке от 4 октября защита ожидается 6 октября 2026 года. Точное время и срок предварительной сдачи подтверждаются объявлением преподавателя. Участие каждого обязательно даже при совпадении с другим экзаменом, порядок решения конфликта нужно согласовать заранее.

Не заучивать незнакомые слова без понимания. Достаточно самостоятельно объяснить цепочку на примере чужой посылки и ответить, что именно планируется проверить.
