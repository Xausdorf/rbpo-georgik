# Проектные решения безопасности

Решения обеспечивают требования из [требований безопасности](security-requirements.md) для приоритетного набора [модели угроз](threat-model.md#приоритетный-набор): T-01, T-02, T-03, T-06, T-10. Процессы P1–P6 и хранилища D1–D4 — по схеме модели угроз.

## Сводка цепочек приоритетного набора

| Угроза | Требования | Решение | Будущая проверка |
| --- | --- | --- | --- |
| T-01 | SR-01, SR-07 | D-01, D-03 | D-01 (чужой ID), D-03 (перевыпуск кода) |
| T-02 | SR-02, SR-03 | D-01 | D-01 (чужое и завершённое задание) |
| T-03 | SR-06, SR-05, SR-10 | D-03 | D-03 (перебор, параллельный перебор) |
| T-06 | SR-03 | D-02 | D-02 (лишнее поле роли, чужие методы, перечень методов) |
| T-10 | SR-07, SR-06 | D-03 | D-03 (поиск кода в ответах, журналах и базе) |

Проверки D-01 и D-03 остаются планом. Для D-02 реализованы вход, серверное назначение роли и политики групп методов; выполненные проверки перечислены в D-02 ниже. Проверки с назначением курьера и изменением отправления требуют будущих методов D-01 и ещё не выполнены.

---

### D-01. Доступ к отправлениям и заданиям только через запросы, ограниченные текущим пользователем

**Контекст.** Отправитель и курьер обращаются к отправлениям и заданиям по идентификатору из запроса (P2, P3). Идентификатор — недоверенный ввод (TB-1, TB-3): его можно подобрать или подставить чужой. Если сервер загружает объект по одному идентификатору, чужие отправления раскрываются (T-01), а курьер получает адреса и действует вне своих заданий (T-02). Актив — персональные данные и статусы в D2.

**Решение.**

- Идентификатор пользователя и роль берутся только из аутентифицированного контекста запроса (D-02), никогда из параметров.
- Все чтения и изменения отправлений и заданий в P2 и P3 идут через единый слой доступа, который строит запрос к базе уже с условием доступа:
  - отправитель: `отправление.ОтправительId = текущий пользователь`;
  - курьер: `задание.КурьерId = текущий пользователь` и `задание активно` (статус `ожидает забора`, `в доставке` или `возврат` для соответствующего типа задания).
- Прямая загрузка отправления по одному идентификатору вне этого слоя запрещена. Исключение — P4 (диспетчер видит все отправления по своей роли) и P5 (поиск только по трек-номеру с урезанным ответом, SR-08).
- Если объект не найден с условием доступа, ответ `404` — такой же, как для несуществующего идентификатора. Так ответ не подтверждает существование чужого отправления.
- Для изменения одного чтения с фильтром недостаточно: принадлежность и активность назначения должны оставаться условиями записи. Изменение отправления и запись события выполняются в одной транзакции с проверкой версий отправления и задания либо эквивалентной атомарной проверкой назначения. Конкурентное завершение или переназначение не должно позволять старому курьеру применить действие после утраты доступа. Это связь D-01 с SR-05 и D-03; механизм ещё предстоит реализовать.
- Ответ формируется отдельной моделью ответа для каждой роли. Модель ответа курьера содержит адрес и телефон; сущность из базы целиком не сериализуется.
- Идентификаторы отправлений и заданий — GUID, но это не основание доступа, а только затрудняет перебор.

**Обоснование.** Условие доступа становится частью самого запроса к данным: объект, к которому нет доступа, просто не выбирается, поэтому обработчик, использующий этот слой, получает только разрешённый объект (принцип полного посредничества и запрета по умолчанию). Одинаковый `404` не раскрывает, существует ли чужое отправление. Модели ответа по ролям ограничивают раскрываемые поля (минимальные привилегии для полей).

**Рассмотренная альтернатива и выбор.**

| | Вариант A: проверка владельца в каждом обработчике после загрузки | Вариант B (выбран): условие доступа внутри запроса через единый слой |
| --- | --- | --- |
| Как работает | `Find(id)`, затем `if (owner != user) return 403` | Запрос сразу содержит условие по владельцу или назначению |
| Сильная сторона | Явно видно в коде обработчика; легко разным ролям задать разные правила | Единое условие применяется уже при чтении; изменение требует атомарной проверки актуального владельца/назначения и версии |
| Слабая сторона | Каждый новый обработчик — новый шанс забыть проверку; `403` отличается от `404` и подтверждает существование объекта | Нужен явный обход для диспетчера; неверно написанное условие ломает доступ сразу во всех обработчиках |
| Компромисс | Простота против риска пропуска | Централизация против риска ошибки в одном месте и неправильного использования обхода |

Выбран B: для продукта, где половина методов работает с чужими по отношению друг к другу объектами, пропуск проверки в одном обработчике (A) ведёт прямо к T-01/T-02, а единое условие (B) позволяет повторно использовать правило доступа. Это не доказательство корректности всех обработчиков: нужны проверка использования слоя и негативные/позитивные тесты каждого метода. **Условие пересмотра:** если отправления станут общими для нескольких пользователей (например, сотрудники одного магазина — условие пересмотра T-01), условие по одному владельцу превращается в условие по членству, и сравнение нужно повторить.

**Связанные угрозы:** T-01, T-02.

**Связанные требования:** SR-01, SR-02, SR-03 (действия курьера только по своему заданию).

**Будущая проверка.** Опирается на критерии SR-01, SR-02 и SR-03; уточняет условия механизма.

- **Условие:** отправители A/B, курьеры K1/K2. Для чтения, отмены и перевыпуска — разные принадлежащие A отправления в допустимых состояниях. Для забора — отдельное назначенное K1 задание в `ожидает забора`; для неудачной попытки — отдельное назначенное K1 задание в `в доставке`. Есть завершённое, отменённое и переназначенное на K2 задания.
- **Действие:** прямые HTTP-запросы с реальными GUID, а не строками шаблонов маршрута.

| Проверка | Запрет / наблюдаемый результат | Разрешённое действие |
| --- | --- | --- |
| Чтение, отмена, перевыпуск чужого отправления | B получает `404` без данных A; состояние, код и журнал не меняются. Отсутствующий GUID даёт тот же ответ для того же метода | A читает своё; на отдельных исходных объектах отменяет `создано` и перевыпускает разрешённый код |
| Список и создание отправлений | B не получает A в `/shipments/my`; `senderId` в теле даёт `400` без создания | Корректное создание B берёт владельца из claims B, новый объект появляется в его списке |
| Чтение и действия курьера | K2 получает `404` по заданиям K1 и не меняет статус, назначение или журнал | K1 читает активное задание и выполняет забор/неудачную попытку на отдельных объектах с правильным исходным статусом |
| Утрата доступа | K1 получает `404` для завершённого, отменённого или переназначенного задания | K2 читает переназначенное ему активное задание |
| Гонка переназначения и действия | Если переназначение уже зафиксировано, запрос K1 не применяет изменение. При конфликте одной исходной версии сохраняется только согласованная операция, без события от отклонённого действия | После назначения K2 законное действие K2 проходит в допустимом состоянии |

Проверки перевыпуска и вручения выполняются после реализации D-03 владельцем этой цепочки. Остальные проверки добавляются вместе с D-01; наличие плана не означает выполненные тесты.

**Допущения.** Идентичность из контекста запроса достоверна (D-02). Все обращения P2 и P3 к D2 идут через слой доступа — нет «сырых» запросов в обход. Статус задания в базе актуален в момент запроса.

**Ограничения и последствия.**

- Не защищает от курьера, который запомнил или сфотографировал адрес во время активного задания: доступ законен.
- Не ограничивает диспетчера: он видит все отправления по своей роли; злоупотребление диспетчера прослеживается только журналом (SR-10).
- Новая обязанность: каждый новый метод P2/P3 должен использовать слой доступа; это проверяется код-ревью и тестом из будущей проверки.

### D-02. Роль определяется только сервером, методы закрыты по умолчанию

**Контекст.** Любой пользователь может напрямую вызвать любой метод API, в том числе увиденный в Swagger (TB-1, TB-3). Если сервер принимает роль из тела регистрации или не проверяет роль на методах диспетчера, пользователь повышает свои права (T-06): получает все отправления и управление назначениями. Актив — роли в D1 и назначения в D2.

**Решение.**

- **Регистрация (P1):** отдельная модель запроса `RegisterSenderRequest` без поля роли. Роль «отправитель» назначает сервер. Неизвестные поля в JSON отклоняются (`JsonUnmappedMemberHandling.Disallow`), поэтому `"role": "dispatcher"` приводит к `400`. Курьеры и диспетчеры создаются только начальным наполнением базы; метода изменения роли в API нет.
- **Аутентификация:** пароли хранятся ASP.NET Core Identity (хеш с солью). При входе выдаётся токен (JWT) со сроком жизни 30 минут; роль в токен записывается из D1.
- **Авторизация — запрет по умолчанию:** резервная политика требует аутентификации для любого метода. Анонимно доступны только явно помеченные `/auth/*`, `/track/*`, `/health`. Группы методов закрыты политиками ролей: `/shipments/*` — отправитель, `/courier/*` — курьер, `/dispatch/*` — диспетчер.
- Проверка «курьер назначен на это задание» — не роль, а условие доступа к объекту (D-01).

**Обоснование.** Роль не может прийти от клиента: её нет в модели запроса, а лишние поля отклоняются. Методы, для которых забыли указать политику, остаются закрытыми (безопасные значения по умолчанию), а роль проверяется на уровне группы методов, а не внутри каждого обработчика (серверное принуждение).

**Рассмотренная альтернатива.** Одна общая модель пользователя для регистрации и управления учётными записями с игнорированием поля роли в коде обработчика. Отклонена: защита держится на том, что разработчик не забудет обнулить поле; любая правка модели возвращает T-06. Отдельная модель без поля убирает саму возможность.

**Связанные угрозы:** T-06.

**Связанные требования:** SR-03.

**Выполненная проверка части D-02.** На настоящем PostgreSQL через Testcontainers проверены: [регистрация](../tests/GetFast.Api.Tests/RegistrationTests.cs) — обычный запрос создаёт только Sender, лишнее поле роли даёт `400` без создания пользователя; [вход](../tests/GetFast.Api.Tests/LoginTests.cs) — Identity проверяет пароль, JWT содержит идентичность и роль из базы, срок 1800 секунд; [политики](../tests/GetFast.Api.Tests/AuthorizationTests.cs) — Sender/Courier получают `403` на `/dispatch/shipments`, Dispatcher получает `200`, а `/courier/tasks` доступен только Courier. Проверены анонимный `401`, подпись, срок, issuer/audience и перечень методов. Заглушки возвращают пустые массивы и не подтверждают изменение назначений.

Ключ `Jwt__SigningKey` проверяется при запуске: минимум 32 байта UTF-8. JWT подписан HS256, issuer `GetFast`, audience `GetFast.Api`; ClockSkew равен нулю. [Проверки конфигурации](../tests/GetFast.Api.Tests/ConfigurationTests.cs) покрывают отсутствие/короткий ключ и границу длины в байтах. В Development миграции применяются и сотрудники создаются из `Seed__*`; [проверки наполнения](../tests/GetFast.Api.Tests/SeedingTests.cs) подтверждают повторяемость и запрет повышения существующего отправителя. В Production автоматического наполнения нет.

**Будущая полная проверка.** Опирается на критерий SR-03, включая методы D-01.

- **Условие:** учётные записи отправителя, курьера и диспетчера; отправление в статусе `создано`.
- **Действие:**
  1. регистрация с `"role": "dispatcher"`, затем вход и `GET /dispatch/shipments`;
  2. токеном отправителя и курьера — `POST /dispatch/shipments/{id}/assign` и `POST /dispatch/shipments/{id}/return`;
  3. без токена — каждый метод, кроме `/auth/*`, `/track/*`, `/health`;
  4. автоматический тест перебирает все зарегистрированные методы приложения и проверяет, что у каждого есть политика ролей либо явная пометка анонимного доступа из разрешённого списка;
  5. диспетчер выполняет назначение.
- **Ожидаемый результат:** 1 — регистрация отклонена (`400`), учётная запись не создана; при обычной регистрации создан Sender и `GET /dispatch/shipments` возвращает `403`; 2 — `403`, назначения, статусы и журнал не меняются; 3 — `401`; 4 — нет методов без политики вне разрешённого списка; 5 — назначение сохранено.

**Допущения.** Ключ подписи токенов хранится вне репозитория и известен только серверу. Роль в D1 меняется только администратором базы (вне модели), поэтому устаревшая роль в токене живёт не дольше 30 минут — для продукта без изменения ролей через API это допустимо.

**Ограничения и последствия.**

- Не защищает от кражи учётных данных сотрудника (вне модели угроз).
- Роль, снятая в базе, действует до истечения токена (до 30 минут). Если появится изменение ролей через API — условие пересмотра T-06 — нужен отзыв токенов или проверка роли по D1 на каждом запросе.
- Новая обязанность: каждый новый метод получает политику; тест из будущей проверки не даст забыть.

### D-03. Код получения: одноразовый, хранится только как HMAC, проверяется атомарно с лимитом попыток

**Контекст.** Вручение подтверждается кодом получения (SR-06). Курьер может перебирать код (T-03), а код может утечь персоналу через ответы API, журналы или базу (T-10). Обе угрозы ведут к краже посылки. Одновременные допустимые из одного состояния запросы (забор и отмена, вручение и неудачная попытка) могут нарушить состояние (T-09).

**Решение.**

- **Генерация:** 6 цифр из криптографического генератора (`RandomNumberGenerator.GetInt32(0, 1_000_000)`) при создании отправления.
- **Хранение:** в D2 хранится только `HMAC-SHA256(ключ, id отправления + код)`. Ключ хранится вне базы и репозитория (в секретах окружения). Открытый код существует кратковременно при генерации и проверке ввода, но не сохраняется. Выдача через API разрешена только в ответе отправителю-владельцу.
- **Показ:** код показывается отправителю один раз — в ответе на создание отправления. Если отправитель потерял код, он перевыпускает его (`POST /shipments/{id}/code`, доступно владельцу до вручения): новый код показывается один раз, прежний перестаёт действовать, в журнал пишется событие без значения кода. Перевыпуск разрешён только в пяти незавершённых статусах, перечисленных в SR-07, при отсутствии блокировки. При генерации проверяется, что новый код отличается от прежнего (сравнение HMAC), иначе генерация повторяется. Счётчик неверных вводов сохраняется: перевыпуск или смена курьера не дают новые пять попыток.
- **Проверка (P3, `/deliver`)** в одной транзакции базы с токеном конкурентности отправления (системный столбец `xmin` PostgreSQL):
  1. отправление в статусе `в доставке`, вручение не заблокировано, курьер назначен (D-01);
  2. сравнение HMAC введённого кода с сохранённым за постоянное время (`CryptographicOperations.FixedTimeEquals`);
  3. неверно — счётчик попыток +1, на 5-й попытке вручение блокируется, событие в журнал;
  4. верно — статус `доставлено`, HMAC кода удаляется (код одноразовый), событие в журнал;
  5. изменение состояния и запись журнала фиксируются вместе; при конфликте токена конкурентности неверная попытка может повториться с перечитанным состоянием и повторной проверкой лимита. Конфликтующий переход статуса отклоняется: его нельзя автоматически применить к новой версии объекта. Неуспешная транзакция не оставляет событие в журнале.
- **Защита от утечки:** модели ответа курьера, диспетчера и публичного отслеживания не содержат поля кода; тела запросов `/deliver` и `/code` не логируются; в журнал событий пишется только «код введён: верно / неверно»; шаблон уведомления SMS не содержит кода.
- Тот же токен конкурентности применяется ко всем переходам статуса (SR-05), поэтому из одной версии состояния проходит только один из конфликтующих допустимых переходов: «забор против отмены» или «вручение против неудачной попытки». Возврат из `в доставке` отклоняется проверкой таблицы переходов, а не служит доказательством защиты от гонки.

**Обоснование.** Миллион вариантов при 5 попытках даёт вероятность угадать не больше 5 из 1 000 000 на отправление. Счётчик меняется в той же транзакции с токеном конкурентности, поэтому параллельные попытки не обходят лимит. HMAC с ключом вне базы означает, что копия базы или ошибка сериализации сущности не раскрывает коды: простой хеш шестизначного кода перебирается мгновенно, а HMAC без ключа — нет. Хранение HMAC сокращает риск утечки из сущности в базе. Защита временного открытого значения в запросе и ответе всё равно требует отключения логирования этих тел и проверки моделей ответа (T-10).

**Рассмотренная альтернатива — сравнение двух способов обеспечить SR-07.**

| | Вариант A: шифровать код и показывать отправителю в карточке в любой момент | Вариант B (выбран): хранить только HMAC, показывать один раз, перевыпуск по запросу |
| --- | --- | --- |
| Удобство | Отправитель в любой момент видит код в карточке | Код виден один раз; потерянный код нужно перевыпустить |
| Что раскрывает ошибка сериализации | Если расшифрованный код добавлен в общую модель карточки, возврат этой модели диспетчеру раскрывает код. Возврат одного шифротекста его не раскрывает | В сохранённой модели есть только HMAC: её сериализация не раскрывает код без ключа. Открытый код всё же есть кратковременно в ответе владельцу и во вводе `/deliver`; ошибки обработки этих данных опасны в обоих вариантах |
| Что раскрывает копия базы без ключа | Шифротекст, из которого нельзя восстановить код без отдельно хранимого ключа | HMAC, по которому нельзя проверить перебор без отдельно хранимого ключа |
| Что раскрывают база и соответствующий ключ | Действующие коды можно расшифровать | Шестизначные коды можно подобрать перебором |
| Новая поверхность | — | Метод перевыпуска кода — новая точка входа (T-01) |

Для обоих вариантов ключ хранится вне базы и репозитория. Сравнение не приписывает HMAC защиту от совместной компрометации базы и ключа; отличие — отсутствие операции повторной расшифровки кода для карточки и принятого риска включить расшифрованное поле в общий ответ.

Выбран B: для службы доставки кража посылки через утёкший код хуже, чем неудобство перевыпуска. **Условие пересмотра:** если код начнут отправлять получателю через SMS-шлюз (условие пересмотра T-10), открытый код окажется во внешней системе (TB-4), и сравнение нужно повторить с учётом срока хранения SMS.

**Обзор решения: контрпример к исходной цепочке.**

- **Исходное предположение** (первая версия SR-07): «код получения известен только отправителю, если сервер не возвращает его персоналу; отправитель видит код в карточке своего отправления».
- **Сценарий, где оно не выполняется:** в варианте A расшифрованный код добавляют в общую модель карточки для показа владельцу. Обработчик диспетчера по ошибке возвращает эту же модель целиком (T-10), раскрывая коды всех включённых в ответ активных отправлений. Шифрование в базе эту ошибку формирования ответа не предотвращает. Одна копия базы без ключа коды не раскрывает; при получении и базы, и ключа можно восстановить коды в варианте A и перебрать их в варианте B. Исходное требование SR-07 описывало только ответы API и не запрещало восстановимое хранение, а его критерий проверял бы лишь заранее известные ответы.
- **Последствия для цепочки:**
  - SR-07 уточнено: код показывается только в ответе на создание и перевыпуск, сервер не хранит его в восстановимом виде; критерий дополнен поиском кода в базе и проверкой перевыпуска;
  - T-01 дополнено: подставив чужой ID в перевыпуск кода, нарушитель получил бы новый код чужого отправления — поэтому перевыпуск закрыт D-01 и включён в его будущую проверку;
  - в модель угроз добавлена точка входа `POST /shipments/{id}/code`;
  - D-03 выбрало вариант B вместо первоначального A.
- **Уточнённая будущая проверка** — ниже, пункты 4–6.

**Связанные угрозы:** T-03, T-10, а также T-01 (перевыпуск кода) и T-09 (конфликт переходов).

**Связанные требования:** SR-06, SR-07, SR-05, SR-10.

**Будущая проверка.** Опирается на критерии SR-06, SR-07 и SR-05; уточняет условия механизма.

- **Условие:** отправление в статусе `в доставке` с известным кодом, назначенный курьер K1, диспетчер; журнал приложения пишет на уровне Information.
- **Действие и ожидаемый результат:**
  1. K1 отправляет 4 неверных кода, затем верный → `доставлено`, повторная отправка того же кода отклонена;
  2. на новом отправлении K1 отправляет 5 неверных кодов, затем верный → вручение заблокировано, статус `в доставке`, в журнале событие блокировки;
  3. на новом отправлении 10 **параллельных** запросов с неверным кодом → счётчик не превышает 5, успешных вручений нет, вручение заблокировано (лимит не обходится гонкой);
  4. отправитель перевыпускает код → старый код отклоняется при вручении, новый принимается;
  5. после прохождения сценариев 1–4 значение каждого выданного кода ищется в ответах всех методов курьера, диспетчера и `/track`, в таблицах базы, в журнале событий, в журнале приложения и в сообщениях заглушки SMS → не найдено;
  6. отправитель B вызывает перевыпуск кода для отправления A → `404`, код A продолжает действовать (связь с D-01);
  7. на отправлении в `ожидает забора` одновременно выполняются забор назначенным курьером и отмена владельцем; на другом отправлении в `в доставке` — вручение с верным кодом и неудачная попытка. Для каждой пары успешен ровно один переход из исходной версии, в журнале ровно одно событие перехода;
  8. после четырёх неверных вводов владелец перевыпускает код → счётчик остаётся 4, следующий неверный ввод блокирует вручение. После пяти неверных вводов перевыпуск отклоняется, блокировка сохраняется. Новый код должен отличаться от прежнего;
  9. перевыпуск в `доставлено`, `отменено`, `возврат`, `возвращено отправителю` → отказ без изменения состояния и журнала.

**Допущения.** Ключ HMAC хранится вне базы и репозитория и недоступен курьерам и диспетчерам. Отправитель передаёт код получателю по своему каналу. Системное время и транзакции PostgreSQL работают штатно.

**Ограничения и последствия.**

- Не защищает от сговора курьера с получателем или отправителем и от получателя, который сам сообщил код постороннему.
- Блокировка после 5 попыток позволяет злонамеренному курьеру намеренно заблокировать вручение; это видно в журнале и решается диспетчером — отказ в обслуживании одного отправления, а не кража.
- Отправитель, потерявший код, должен перевыпустить его — дополнительное действие в сценарии.
- Если ключ HMAC скомпрометирован вместе с базой, коды перебираются; ключ нужно заменить, а коды активных отправлений перевыпустить.
