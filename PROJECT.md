## 1. Назначение

GetFast — серверное приложение (веб-API) городской курьерской службы доставки посылок «от двери до двери». Отправитель оформляет посылку и узнаёт стоимость, диспетчер распределяет задания между курьерами, курьер забирает посылку и вручает её получателю по коду получения. Получатель следит за посылкой по трек-номеру без регистрации.

Собственная логика продукта: расчёт стоимости по тарифу, жизненный цикл отправления с допустимыми переходами между статусами, назначение курьеров, вручение по коду, обработка неудачных попыток доставки и возврат посылки отправителю.

## 2. Граница продукта

**В продукт входит:**

- серверное API для отправителей, курьеров, диспетчеров и получателей;
- расчёт стоимости доставки по весу и тарифной зоне;
- жизненный цикл отправления: создание, отмена, забор, доставка, неудачная попытка, перенос, возврат;
- назначение курьеров на задания забора и доставки;
- выдача, перевыпуск и проверка кода получения;
- публичное отслеживание по трек-номеру;
- журнал событий отправления: кто, когда и какое действие выполнил;
- хранилище данных.

**Внешнее окружение и внешние системы:**

- клиентские приложения: в рамках курса вместо них используются Swagger UI и HTTP-запросы;
- SMS-шлюз для уведомлений получателя о статусе — только заглушка, сообщения записываются в журнал приложения. Код получения через SMS не отправляется: его передаёт получателю отправитель (см. SR-07);
- оплата — происходит вне системы, продукт только рассчитывает и хранит стоимость.

**Команда сознательно не реализует:**

- приём платежей и интеграцию с платёжными системами;
- карты, геолокацию курьеров и построение маршрутов;
- сортировочные центры, склады и межгородскую доставку — работа идёт в пределах одного города;
- мобильные приложения и полноценный frontend;
- реальную отправку SMS и push-уведомлений;
- рейтинги, чат, промокоды и скидки;
- самостоятельную регистрацию курьеров и диспетчеров: их учётные записи создаются начальным наполнением базы.

## 3. Пользователи и доступные действия

| Пользователь или роль | Кто это | Что может делать | Что ему недоступно |
| --- | --- | --- | --- |
| Отправитель | Зарегистрированный клиент: частное лицо или небольшой магазин | Рассчитать стоимость; создать отправление; видеть свои отправления и их историю; отменить отправление до забора; получить код получения при оформлении, чтобы передать его получателю; перевыпустить код, если он потерян | Видеть чужие отправления; задавать стоимость самому; менять адрес и получателя после забора; менять статус доставки |
| Получатель (без входа) | Человек, которому адресована посылка; учётной записи в системе нет | По трек-номеру видеть статус и ожидаемую дату; после неудачной попытки перенести доставку на другой день, подтвердив последние цифры своего телефона | Видеть адрес забора и данные отправителя; видеть объявленную ценность; переносить доставку больше установленного числа раз; менять адрес доставки |
| Курьер | Сотрудник службы | Видеть только назначенные ему задания; видеть адрес и телефон только в своих активных заданиях; подтвердить забор; вручить посылку по коду; отметить неудачную попытку с причиной | Видеть чужие задания и отправления вне своих заданий; назначать задания себе или другим; отмечать вручение без верного кода; видеть данные по завершённым заданиям |
| Диспетчер | Сотрудник службы, координирующий работу | Видеть все отправления и журнал событий; назначать и переназначать курьеров; оформлять возврат после неудачных попыток; разбирать спорные ситуации | Отмечать вручение вместо курьера; узнавать код получения; удалять отправления и записи журнала; изменять стоимость уже созданного отправления |

## 4. Сквозные сценарии

### Сценарий 1. Оформление отправления и забор посылки

- **Участники:** отправитель, диспетчер, курьер.
- **Начальное условие:** отправитель зарегистрирован и вошёл в систему; у службы есть свободный курьер.
- **Основные действия:** отправитель указывает адрес забора, получателя (имя, телефон, адрес), вес, габариты и объявленную ценность → сервер рассчитывает стоимость по тарифу и зоне → отправитель подтверждает оформление и получает трек-номер и код получения → диспетчер назначает курьера на забор → курьер приезжает и подтверждает забор. До забора отправитель может отменить отправление.
- **Результат:** посылка находится у службы и готова к доставке.
- **Какие данные или состояние изменяются:** создаётся отправление, стоимость фиксируется, генерируется код получения; статус меняется: `создано` → `ожидает забора` → `забрано` (или `отменено`); в журнал добавляются события.

### Сценарий 2. Доставка и вручение по коду

- **Участники:** диспетчер, курьер, получатель.
- **Начальное условие:** отправление в статусе `забрано`; получатель знает код получения от отправителя.
- **Основные действия:** диспетчер назначает курьера на доставку → курьер видит адрес и телефон получателя в своём задании → при встрече получатель называет код → курьер вводит его → сервер проверяет код и число попыток ввода.
- **Результат:** посылка вручена; отправитель и получатель видят статус `доставлено`.
- **Какие данные или состояние изменяются:** статус `забрано` → `в доставке` → `доставлено`; фиксируются время вручения и курьер; код становится недействительным; курьер теряет доступ к адресу и телефону получателя.

### Сценарий 3. Неудачная попытка, перенос и возврат

- **Участники:** курьер, получатель, диспетчер, отправитель.
- **Начальное условие:** отправление в статусе `в доставке`.
- **Основные действия:** курьер не застал получателя и отмечает неудачную попытку с причиной → получатель по трек-номеру видит статус и, подтвердив последние цифры телефона, выбирает новый день доставки → диспетчер назначает повторную доставку. Если допустимое число попыток исчерпано или получатель отказался, диспетчер оформляет возврат → курьер возвращает посылку отправителю, и тот подтверждает получение.
- **Результат:** посылка вручена со второй попытки либо возвращена отправителю.
- **Какие данные или состояние изменяются:** счётчик попыток и переносов, дата доставки, статус `в доставке` → `неудачная попытка` → `в доставке` / `возврат` → `возвращено отправителю`; записи в журнале.

## 5. Значимые данные и другие объекты

| Данные или объект | Для кого имеют значение | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |
| --- | --- | --- | --- |
| Отправление: адреса, имена и телефоны отправителя и получателя, описание, объявленная ценность | Отправитель, получатель, служба | Раскрытие персональных данных и домашних адресов; сведения о ценных посылках полезны злоумышленнику | Подмена адреса или получателя отправляет посылку не тому человеку; удаление — посылка «теряется» в системе |
| Код получения | Получатель, отправитель | Любой, кто знает трек-номер и код, может получить чужую посылку | Если вручение отмечено без верного кода, нельзя доказать, кому передана посылка; служба несёт ответственность за утерю |
| Статус отправления и назначения курьеров | Все участники | Раскрытие назначений показывает, у какого курьера и когда находится ценная посылка | Ложный статус «доставлено» или «отменено» скрывает утерю; два курьера на одном задании или задание без курьера — срыв доставки |
| Стоимость и тариф | Отправитель, служба | Мало значимо | Заниженная стоимость — прямой убыток службы; завышенная — претензии клиента |
| Журнал событий отправления | Диспетчер, служба при разборе претензий | Раскрывает перемещения посылки и действия сотрудников | Изменение или удаление записей не позволяет установить, кто отвечает за утерю или повреждение |
| Учётные записи и роли | Служба | Раскрытие учётных данных даёт доступ к чужим заданиям | Самовольная смена роли (например, курьер становится диспетчером) даёт доступ ко всем отправлениям |

## 6. Компоненты и внешние взаимодействия

Актуальная схема, точки входа и границы доверия — в [модели угроз](docs/threat-model.md#модель-продукта).

- **Клиенты** (Swagger UI, HTTP-клиент) — через них работают отправитель, курьер и диспетчер после входа в систему; получатель работает с публичными методами отслеживания без входа.
- **Сервер GetFast API** — проверяет права, рассчитывает стоимость, управляет статусами, назначениями и кодами, ведёт журнал.
- **База данных** — хранит пользователей, отправления, задания, тарифы и журнал событий. Доступ к ней есть только у сервера.
- **Заглушка SMS-шлюза** — сервер передаёт ей номер телефона и текст уведомления о статусе; заглушка записывает сообщение в журнал приложения вместо реальной отправки.

Основные взаимодействия:

- клиент → API: учётные данные, данные отправления, действия с заданиями, код получения;
- получатель → публичное API: трек-номер, последние цифры телефона, новая дата доставки;
- API → база данных: чтение и изменение отправлений, заданий, журнала;
- API → заглушка SMS: номер телефона и текст уведомления.

## 7. Откуда продукт получает данные

| Источник | Пример данных | Кто управляет источником | Как продукт использует данные |
| --- | --- | --- | --- |
| Запросы отправителя | Адреса, имя и телефон получателя, вес, габариты, объявленная ценность | Отправитель | Создание отправления, расчёт стоимости |
| Запросы курьера | Идентификатор задания, введённый код получения, причина неудачной попытки | Курьер | Смена статуса, проверка кода, запись в журнал |
| Запросы диспетчера | Назначение курьера, решение о возврате | Диспетчер | Изменение назначений и статусов |
| Публичные запросы получателя | Трек-номер, последние цифры телефона, новая дата доставки | Любой пользователь интернета | Показ статуса, перенос доставки |
| Начальное наполнение базы | Тарифы и зоны, учётные записи курьеров и диспетчеров | Команда | Расчёт стоимости, вход сотрудников |

## 8. Минимальное функциональное ядро

**Обязательные функции:**

- вход в систему для отправителей, курьеров и диспетчеров; регистрация отправителей;
- расчёт стоимости по весу и зоне;
- создание и отмена отправления, трек-номер и код получения;
- назначение курьера диспетчером на забор и доставку;
- подтверждение забора, вручение по коду, отметка неудачной попытки;
- публичное отслеживание статуса по трек-номеру;
- оформление возврата диспетчером;
- журнал событий отправления.

**Функции, которые можно исключить при нехватке времени:**

- перенос доставки получателем: тогда после неудачной попытки новую дату назначает диспетчер;
- ограничение числа попыток ввода кода и числа переносов;
- уведомления через заглушку SMS;
- объявленная ценность и тарифные зоны (заменяются единым тарифом по весу);
- подтверждение возврата отправителем.

## 9. Стек и путь к первой работающей версии

**Основные технологии:** C#, .NET 10, ASP.NET Core Web API, Entity Framework Core, PostgreSQL, Docker Compose для локального запуска базы, xUnit для тестов, Swagger UI (OpenAPI) как клиент.  
**Технологии, новые для команды:** _уточнить командой_  
**Внешние сервисы, необходимые для запуска:** только PostgreSQL в локальном контейнере; SMS-шлюз заменён заглушкой.  
**Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов:** реальных внешних сервисов в ядре нет; уведомления записываются заглушкой в журнал, поэтому все сценарии проходят локально.

**Что команда реализует первым, чтобы получить запускаемую версию:** проект ASP.NET Core Web API с проверкой работоспособности `GET /health`, подключением к PostgreSQL и миграцией для сущности «Отправление»; затем создание отправления и получение его статуса по трек-номеру.
